# gentle-profiles

Pi/gentle-shell extension package that provides named account profiles (for example `work` and `personal`) covering claude-bridge, openai-codex and native anthropic credentials, plus a minimal launcher. Linux, macOS, Windows. Published as a Gentle Hub listed package.

## Specs

- S1. The deliverable is a package "como los de: https://gentlemanprogramming.com/gentle-hub/": a public repo with the `gentle-shell-package` and `gentle-shell-extension` GitHub topics, installable with `pi install npm:gentle-profiles`.
- S2. Purpose, verbatim: "tener multicuenta de claude/codex o cualquier otra en gentle-shell, obviamente usar claude-brige para cada una. Pero asi tener perfiles de distinta cuenta, ejemplo: Work y Personal."
- S3. "Debe funcionar para gentle-shell en Linux y Mac y Windows."
- S4. Form chosen by the user: "Extensión /profile + launcher mínimo". The extension provides a `/profile` slash command; the launcher is a CLI that starts gentle-shell with a given profile.
- S5. Providers in v1 chosen by the user: "Claude via claude-bridge", "Codex (openai-codex de pi)", "Anthropic nativo de pi (API key / OAuth)".
- S6. Profile storage lives under the pi agent dir: `<agentDir>/profiles/<name>/` with a `claude/` directory used as `CLAUDE_CONFIG_DIR` for claude-bridge and an `auth.json` holding that profile's pi credentials (`openai-codex`, `anthropic`). `<agentDir>/profiles/current` records the active profile name.
- S7. `/profile` with no argument shows an interactive picker of existing profiles and switches to the selected one. `/profile <name>` switches directly. `/profile create <name>`, `/profile delete <name>`, `/profile list`, `/profile current` are the subcommands. Names match `^[a-z0-9][a-z0-9_-]{0,31}$`; an invalid name is rejected with the message `Invalid profile name "<name>": use lowercase letters, digits, "-" or "_" (max 32 chars).` and nothing changes.
- S8. Switching a profile: saves the current live pi credentials for the covered providers into the outgoing profile's `auth.json`, loads the incoming profile's `auth.json` entries into pi's live credentials, sets `CLAUDE_CONFIG_DIR` for the running process to the incoming profile's `claude/` dir, and writes `profiles/current`. Credentials of providers not covered by S5 are left untouched. Switching to the active profile is a no-op that prints `Already on profile "<name>".`
- S9. Deleting the active profile is refused with `Cannot delete the active profile "<name>". Switch to another profile first.` Deleting a non-existent profile prints `Profile "<name>" does not exist.` Deleting asks for confirmation in the UI before removing the directory.
- S10. The launcher `gentle-profiles <name> [gentle-shell args...]` sets `CLAUDE_CONFIG_DIR` to the profile's `claude/` dir, writes `profiles/current`, syncs the profile's `auth.json` entries into the agent dir's live `auth.json` (same rules as S8), then execs `gentle-shell` with the remaining args. A missing profile prints `Profile "<name>" does not exist. Create it with: gentle-profiles create <name>` and exits with code 1. `gentle-profiles list`, `gentle-profiles create <name>`, `gentle-profiles current` mirror S7 without a UI.
- S11. On extension load, if `profiles/current` names an existing profile, the extension sets `CLAUDE_CONFIG_DIR` for the process to that profile's `claude/` dir (unless the environment already sets it), so the bridge uses the right login even when gentle-shell was started without the launcher. If no profile exists, the extension creates `default` from the live credentials and the current Claude Code config dir path (recorded, not copied).
- S12. Logging into a profile's Claude account is done by running `claude auth login` with that profile's `CLAUDE_CONFIG_DIR`; `/profile login claude` runs it for the active profile and prints the exact command on platforms where an interactive child cannot be opened. Codex and anthropic logins reuse pi's `/login` and are captured by the next switch (S8).
- S13. All paths are built with Node `path` APIs and the agent dir resolved by pi (`PI_CODING_AGENT_DIR` or the platform default), never with hard-coded `~` or `/`; the launcher resolves `gentle-shell` through `PATH` on every platform, including `.cmd` shims on Windows.
- S14. Docs: README with install, Gentle Hub topics, the profile layout from S6, every command from S7/S10, and the Windows notes from S13.

- S15. The active account is shown in Gentle Shell's status bar and sidebar through `ctx.ui.setStatus("gentle-profiles", text)` (never `setFooter`, which Gentle Shell owns; the Gentle Shell command palette is a closed catalog and is not extended). The text is `<profile> · <email>` where the email is `oauthAccount.emailAddress` read from `<claudeDir>/.claude.json` of the active profile (for a Claude dir equal to `<home>/.claude` it also falls back to `<home>/.claude.json`); when no email can be read the text is `<profile> · not logged in`; with no active profile the status is cleared (`undefined`). It is refreshed on session start, after a successful `/profile` switch, and on `/profile current`. Reading never throws and never exposes tokens.
- S16. The `default` profile (created from an existing login) uses Claude Code's built-in default config dir, so `CLAUDE_CONFIG_DIR` must be left **unset** (deleted from the process env, and from the child env in the launcher) while it is active; it must never be set to `<home>/.claude`. A marker file `claude-default` in the profile dir records this; legacy profiles whose `claude-dir` resolves to `<home>/.claude` are treated the same way. Switching to such a profile removes the variable (`delete`, never assigning the string "undefined"). `/profile login claude` and `gentle-profiles login` for it use plain `claude auth login` with no env prefix; `/profile current` shows `CLAUDE_CONFIG_DIR=(unset: Claude Code default)`. A user-set `CLAUDE_CONFIG_DIR` in the environment at first run is still recorded and kept.
- S17. Status text is `gentle-profiles: <profile> · <masked email>` when logged in and `gentle-profiles: <profile> · not logged in` otherwise (the plugin label is one exported constant). The mask keeps the first `min(4, max(1, localLength - 3))` characters of the local part, then `****`, then the untouched `@domain` (example: `fcir****@gmail.com`). The full email must never appear in any status or notification.
- S18. Login detection uses `claude auth status` as primary source (JSON on stdout with `loggedIn` and `email`), run with the profile's `CLAUDE_CONFIG_DIR` (or with the variable removed for S16 profiles), through `execFile` with fixed arguments (`shell: true` only on win32 for `.cmd` shims), a 5 s timeout, never throwing; the `.claude.json` `oauthAccount` reader is the fallback when the CLI is missing, times out or prints no JSON. The status refreshes on session start, after a switch, on `/profile current`, on `agent_end`, and every 60 s through an unref'd timer cleared on session shutdown. Overlapping refreshes are skipped, and a result computed for a previous profile never overwrites a newer one.
- S19. The plugin is renamed to `gentle-accounts`. The npm package, the GitHub repository and the release-please `package-name` are `gentle-accounts`; the launcher binary is `gentle-accounts` (`bin/gentle-accounts.mjs`); `PLUGIN_LABEL` and the status key are `gentle-accounts` so the status reads `gentle-accounts: <profile> · <masked email>`. The only slash command is `/gentle:accounts` with the same sub-commands as the old `/profile` (list, current, create, delete, login claude, help, `<name>`, no argument = picker); `/profile` is removed on purpose (user decision L12). All user-facing text (help, usage, notifications, README, CLI messages such as `Create it with: gentle-accounts create <name>`) uses the new names. The on-disk layout (`<agentDir>/profiles/...`), the notion of a "profile" and every behavior of S1-S18 stay unchanged.
- S20. The README is in Spanish: `README.md` is the Spanish version and the previous English text is kept as `README.en.md`; both start with a language switch line linking to each other. Commands, file names, paths, status examples, code blocks and option names are identical in both files (only prose, headings and table text are translated). Neutral Latin American Spanish, no voseo.
- S21. It skips when the commit already has a tag (re-runs are idempotent). The next version comes from `scripts/next-version.ts` (pure function plus a small CLI), never from shell interpolation of commit text: no tag yet gives `0.1.0`; otherwise parse the latest `vX.Y.Z` reachable tag and the merge commit message (the squashed PR title and body): a Conventional Commit with `!` after the type or a `BREAKING CHANGE:` / `BREAKING-CHANGE:` footer is breaking; while the major is 0, breaking and `feat` bump the minor and everything else, including non-conventional titles, bumps the patch; from major 1, breaking bumps the major, `feat` the minor, everything else the patch. The Release is created with `gh release create vX.Y.Z --target <sha> --generate-notes`. `package.json` `version` is not rewritten on `main` (direct pushes are blocked); this is documented. The PR title check stays. Both READMEs describe the new flow and no longer mention a release PR or `RELEASE_PLEASE_TOKEN`.
- S22. `/gentle:accounts login claude` highlights the command it prints instead of burying it in a sentence: a short intro line saying to run it in ANOTHER terminal because it opens the browser, a blank line, the command alone on its own line indented and prefixed with `$ ` (`PS> ` on Windows), a blank line, then one line pointing to the launcher alternative (`gentle-accounts login <profile>`) and one line saying to run `/gentle:accounts current` afterwards to see the account. The command text itself (`claudeLoginCommand`) does not change. Running `claude auth login` from inside the pi TUI is deliberately not done: it is interactive (browser flow), the TUI owns the terminal, and it cannot be verified without a real account; the launcher command `gentle-accounts login <profile>` is the supported way to run it.

- S27. A startup profile decides which profile new sessions start on, instead of always the last used one. It is stored in `<agentDir>/profiles/startup` (the profile name; absent means "last used", today's behavior). `/gentle:accounts startup` shows it; `/gentle:accounts startup <name>` sets it (must exist, name rules of S7); `/gentle:accounts startup last` clears it. The CLI mirrors it: `gentle-accounts startup [<name>|last]`. Messages: `Startup profile set to "<name>". New sessions start on it.`, `Startup profile cleared. New sessions start on the last used profile.`, show: `Startup profile: <name>` or `Startup profile: none (new sessions start on the last used profile: <current>)` (`<current>` is `none` when there is no active profile); unknown profile: `Profile "<name>" does not exist.`; invalid name: the S7 message. On session start, after the first-run `default` creation, if a startup profile is set and differs from the active one, the extension switches to it with the same safe switch as S8 (read every file before writing, snapshot the outgoing credentials, set or delete `CLAUDE_CONFIG_DIR` per S16) and notifies `Started on profile "<name>" (startup profile).`; when it already is the active one nothing changes; a corrupt file or a missing startup profile notifies an error and never breaks the session. An explicit `gentle-accounts <name>` launch still wins for that launch. Mechanism: the launcher sets `GENTLE_ACCOUNTS_LAUNCH_PROFILE=<name>` in the environment of the `gentle-shell` it starts (gentle-shell builds the child environment from its own, verified in `gentle-shell-launcher.mjs`), and the extension skips the startup switch at session start whenever that variable is non-empty (the launcher already switched to `<name>`). The startup switch only runs when the process starts (`SessionStartEvent.reason` is `"startup"`, or absent): `new`, `resume`, `fork` and `reload` keep a profile the user switched to by hand (found by the independent verification, L22). A startup file that names a profile that no longer exists is reported at session start with the warning `Startup profile "<name>" does not exist; starting on the last used profile.` and nothing changes. Deleting the startup profile is refused: `Cannot delete the startup profile "<name>". Set another one or clear it with "startup last" first.` The scope is global to the agent dir: concurrent sessions share `auth.json` and `profiles/current`, so a new session that switches profile also changes the credentials the other open sessions read (documented as a known limit; per-session isolation is out of scope).
- S28. The status text gets an icon in front, the same style as other Gentle Shell statuses: `👤 gentle-accounts: <profile> · <masked email>` when logged in and `🔒 gentle-accounts: <profile> · not logged in` otherwise. Everything else of S17 stays (masking, no active profile clears the status). The images generated from `statusText` and every doc example are updated.
- S29. The email shown in the status bar is a setting, hidden by default. It is stored as `showEmail` (boolean, default `false`) in `<agentDir>/profiles/settings.json`; a missing, empty or invalid file means the default and is never rewritten on read; writing preserves any other key and uses the same atomic write as the auth files with mode 0600. `/gentle:accounts email` shows the current value (`Email display: hidden (masked in the status bar)` or `Email display: shown (full email in the status bar)`); `/gentle:accounts email show` and `/gentle:accounts email hide` set it and print `Email display set to shown. The status bar shows the full email.` / `Email display set to hidden. The status bar shows a masked email.`; any other argument prints `Usage: /gentle:accounts email [show|hide]` as a warning. The status bar is refreshed right after a change. The CLI mirrors it: `gentle-accounts email [show|hide]` (usage error exits 1). `statusText` takes the setting: hidden keeps S17/S28 (`👤 gentle-accounts: <profile> · <masked email>`), shown prints the full address in the same place. The full email is only ever written to the status bar and only when the setting is `shown`: no notification, log, command output or image contains it in either mode. `help`/usage, argument completions, docs and README list the command, and the docs warn that the full email is visible to anyone who sees the screen.
- S30. Each session started by the launcher gets its own private agent home, so several projects can run at the same time with a different account each (user requirement L23: "es clave poder trabajar en varios proyectos con distinta account en cada una"). Recipe (validated by the spike, Log L24): `gentle-accounts <name> [args]` builds `H = <os.tmpdir()>/gentle-accounts/<uuid>` (mode 0700) containing (a) a symlink for every entry of the shared agent dir except `auth.json`, `settings.json`, `auth.json.*`, `*.lock` and names starting with `.gentle-` (directories as junctions on Windows; file entries fall back to a hard link, then to a copy, on Windows; re-scan at build time), (b) its own real `auth.json` (mode 0600) copied from the profile snapshot (`{}` when empty; providers no profile covers come from the shared live `auth.json`; when the profile is the global current one, each covered provider takes the fresher of the shared live and snapshot entries, whole: the `oauth` entry with the larger numeric `expires`, otherwise the shared live entry; the shared live `auth.json` is never written on copy-back), (c) a generated `settings.json` copied from the shared one with every relative local-path entry of `packages` resolved against the shared agent dir and written as an absolute path (a plain symlink or a relative copy silently fails to load the extension), and (d) a marker `.gentle-accounts-session.json` with `{ "version": 1, "sharedAgentDir": <realpath>, "profile": <name>, "pid": <launcher pid>, "createdAt": <iso> }`. It then runs `gentle-shell --home H [args]` with `GENTLE_SHELL_NO_AUTO_SETUP=1` (gentle-shell sets PI_CODING_AGENT_DIR itself; never add a `.gentle-shell-home` marker) plus the existing `CLAUDE_CONFIG_DIR` rule (S16) and `GENTLE_ACCOUNTS_LAUNCH_PROFILE`. When gentle-shell exits (any exit code, SIGINT, SIGTERM) the launcher copies the covered providers of `H/auth.json` back into the snapshot of the session's current profile (write to a unique temp name then rename; a failure is reported on stderr and never deletes `H/auth.json`) and removes `H` without following links (unlink symlinks, rmdir junctions, never a recursive delete through them). At launcher start it sweeps homes under `<os.tmpdir()>/gentle-accounts/` whose marker pid is dead (same copy-back then removal). Sessions that were NOT started by the launcher keep today's global behavior unchanged. Extension, when `getAgentDir()` contains the marker (session mode): the shared store (profiles, snapshots, Claude dirs, startup, settings.json of profiles) uses the canonical `sharedAgentDir`; the live auth file is `H/auth.json`; the session's current profile lives in `H/.gentle-accounts-current` (never in `profiles/current`); every switch, snapshot and status refresh works exactly as before on those paths; the first-run `default` creation is race safe (an existing folder is not an error) and every temp file name is unique (pid + random), so two sessions starting at once never collide. The session profile defaults to the marker `profile`. The startup profile and `profiles/current` are not applied in session mode (the launcher already chose the profile). `claudeDir()` always resolves through the canonical shared path so the macOS keychain key does not depend on the private home. Windows fallbacks (junction, hard link, copy) are covered by unit tests with an injected fs facade; they are not exercised on a real Windows machine.
- S31. A menu for accounts in the style of Gentle Shell's native `/gentle:profiles` panel (overlay opened with `ctx.ui.custom`, rounded frame, one tab per profile with the active and startup markers, rows per provider with their state, key hints, Esc to close, arrows/enter/shortcuts) opened by `/gentle:accounts menu` and by `/gentle:accounts` without arguments when the UI is available. Actions: switch, create, delete (confirm), set or clear the startup profile, toggle the email display, add an account for a provider (S32), and open the current project with a profile in a NEW session (S32). It returns a tagged action to the caller loop (as the native panel does), never writes outside the existing store functions, and shows feedback inside the panel. Plain `select` fallback when custom overlays are unavailable.
- S32. Adding an account offers where to run the login: in a new terminal tab or in the same terminal. For Claude the command is `claude auth login` with the profile's `CLAUDE_CONFIG_DIR`. Same terminal: the `ctx.ui.custom` hand-over pattern (stop the TUI, spawn with inherited stdio, ignore SIGINT while the child runs, always restore the TUI and call `done`, refresh the model registry and the status afterwards); the precedent is `gentle-pi/extensions/gentle-music.ts` (`runInherit`, `handOverTerminal`). New tab: `osascript` for Terminal.app and iTerm2 on macOS (chosen from `TERM_PROGRAM`), `wt -w 0 nt` on Windows, `$TMUX` new-window, `gnome-terminal --tab`, `konsole --new-tab`, `kitty @ launch`, `wezterm cli spawn` on Linux, in that detection order; when no terminal can be opened the command is printed (S22 layout). For providers whose login is pi's internal `/login` (Codex, Anthropic and every other account provider stored in auth.json) an extension cannot run it: the editor is prefilled with `/login` (`ctx.ui.setEditorText`) and the user presses Enter. "Open this project with another account" starts `gentle-accounts <profile>` in the same working directory in a new tab (S30), falling back to printing the command.
- S33. README and docs (both languages) describe the menu, the per-session accounts and the login options, and the repository description stays in Spanish.
- S34. Antigravity (Google) multi-account is a planning item only: pi 1.5.x ships no Antigravity or Gemini CLI provider (`google` and `google-vertex` are API-key providers), so a custom OAuth provider for pi has to exist first. Preparation: stop hard-coding two providers in `COVERED_PROVIDERS` and treat every account-based provider stored in `auth.json` as covered (an exclusion list for pure API-key providers is configurable), so any provider that registers later works without changes. A written plan (research questions, options, risks) is produced in `docs/` before any code.
